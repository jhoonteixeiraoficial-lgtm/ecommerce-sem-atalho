# Assertive Real-Browser Quality Design

## Goal

Make the existing Assertive listing flow work consistently in a real browser before resuming multi-tenant scaling. A successful analysis must produce useful, factual copy and an explicit image result for photo, URL, and description inputs. Users must also be able to reopen and edit listing attributes.

This work does not publish a Mercado Livre item during automated or controlled smoke tests.

## Current Failure Evidence

- Production is still on commit `03ce68d`, while the governed image pipeline exists only from `35f1107` onward.
- Production has no `ASSERTIVE_IMAGE_ENHANCEMENT_ENABLED` setting, and enhancement is enabled only when that value is exactly `true`.
- Recent browser analyses stored no `photo_asset_ids`, so they bypassed `buildListingGallery` entirely.
- URL and description analyses can reach the editor with an empty gallery.
- The image asset migration was absent from the remote database. It was applied on 2026-09-10 before implementation began.
- The copy generator can replace a complete AI description with a very short factual fallback when one unsupported claim is detected.
- The editor displays attributes but has no explicit mode for reopening and saving the complete attribute set.

## Image Behavior

### User Photo

The uploaded original remains private evidence. The pipeline creates a normalized publication rendition for every accepted upload. It attempts AI cleanup for the cover when the feature is enabled. The enhanced cover replaces the normalized cover only after the fidelity gate returns `ACCEPT`; otherwise the normalized image remains visible and usable.

The editor labels each image as `Original normalizada` or `Melhorada por IA`. A rejected or failed enhancement is visible as a warning and never produces an empty gallery.

### URL

Images discovered at the submitted URL are ingested as private `SOURCE_REFERENCE` assets with `REFERENCE_ONLY` rights. They are not attached directly to the publishable gallery.

The main reference image, confirmed product identity, and confirmed product facts ground one new AI-generated cover. The generated asset is stored as `GENERATED_SCENE`, marked as generated by AI, and passed through the fidelity gate against the reference. A fidelity rejection remains a visible generation failure and can be retried; it does not fall back to publishing the reference image.

If the URL exposes no usable reference image, the flow follows the description rule after identity confirmation.

### Description

Text-only generation starts only when the product truth has confidence of at least `0.7`, a confirmed product type, and at least one confirmed discriminating fact such as brand, model, variant, material, or color. Otherwise the analysis remains `needs_input` and asks for the missing identity data.

Once eligible, the confirmed truth brief grounds one AI-generated cover. Since no visual source exists, fidelity checks structural image quality and prompt compliance rather than visual identity. The editor explicitly warns that the result is an AI representation requiring visual review.

### Confirmation And Publication

AI-generated URL and description images require an explicit user confirmation before publication. Confirmation is stored in the listing's governed image-review metadata through a dedicated endpoint that verifies the asset belongs to the user and is attached to that listing. User-uploaded images and fidelity-approved cleanup of those images do not require this extra confirmation.

Publication readiness blocks while a generated asset is pending review. The editor offers `Confirmar imagem`, `Gerar outra opção`, and `Enviar foto própria`. A generation/provider failure is displayed with a retry action instead of silently returning an empty gallery.

The initial synchronous scope generates one cover. Additional generated scenes are outside this delivery; users can request another cover or add owned photos without paying the latency and cost of generating an entire gallery automatically.

## Asset Model

The existing asset registry remains the source of truth. A follow-up migration allows a `GENERATED_SCENE` created from a text-only brief to have no parent asset. Such an asset must retain a truth-brief hash, prompt hash, provider, model, and `LICENSED` rights metadata. Reference-grounded generated assets retain the reference as their parent.

Publication eligibility is updated so a generated scene may be parentless only when its provenance metadata is complete and the listing review metadata confirms it. Competitor and `REFERENCE_ONLY` assets remain non-publishable.

The image pipeline receives one explicit source mode instead of inferring behavior from an optional array:

- `OWNED_UPLOAD`: normalize all assets and optionally enhance the cover.
- `URL_REFERENCE`: ingest references and generate a cover.
- `TEXT_BRIEF`: generate a cover from confirmed truth.

This prevents the current silent branch where an empty `photo_asset_ids` array skips all image work.

## Copy Quality

Title generation evaluates the primary result and alternatives against the same factual brief. It selects the highest-scoring accepted title using protected identity coverage, useful keyword coverage, absence of repetition, complete trailing token, and the category limit. It never pads the title with unsupported measurements or claims.

Description validation changes from all-or-nothing fallback to section-level repair. Unsupported measurements, warranty, certification, compatibility, or package claims are removed or regenerated, while valid commercial structure and factual benefits remain. The final copy contains:

- a concise factual opening;
- verified product benefits derived from its confirmed function;
- confirmed highlights and specifications;
- a buyer-check section when important information is still missing.

The generator performs one constrained retry when the result is empty, structurally incomplete, or below a quality floor supported by the available facts. It does not invent content merely to reach a character count. The editor surfaces whether the result was accepted directly, repaired, or generated by deterministic fallback.

## Attribute Editing

The listing editor adds an `Editar atributos` action for unpublished listings. It opens an inline form containing the complete current attribute list plus unresolved attributes. Enumerated Mercado Livre attributes use their official options; free-text attributes use bounded text fields.

Saving replaces the governed attribute list through the existing listing PATCH endpoint, invalidates prior preflight data, recomputes completeness and readiness, and returns the editor to read mode. Cancel restores the server value. Published listings remain read-only.

## Error Handling And Observability

Every image path records stage events with the source mode, asset counts, provider/model, outcome, duration, and a stable error code. Logs and browser responses do not expose credentials or raw provider payloads.

Expected image outcomes are `enhanced`, `normalized_fallback`, `generated_pending_review`, `generation_failed`, and `identity_required`. An analysis may continue to copy/attribute editing after a recoverable image failure, but the editor must explain why the gallery is not publication-ready.

Copy stages record selected-title score, repair/fallback mode, and reason codes. They do not store prompts containing secrets.

## Validation

Implementation follows test-driven development:

1. Add failing unit tests for source-mode selection, text-only generated assets, URL references, review gating, title selection, partial description repair, and attribute editing state.
2. Add route/integration tests proving no input mode silently skips its image outcome.
3. Run the full Vitest suite, generated Next.js types, typecheck, lint, and production build.
4. Use a disposable authorized Supabase user and a user-owned fixture image in a real headless Chromium session.
5. Exercise photo, URL, and description from the UI through the editor. Assert image labels/review controls, non-empty factual title and description, editable attributes, and no browser/network errors.
6. Use real Gemini calls for controlled image and copy smoke tests. Do not call the Mercado Livre publish endpoint.
7. Deploy the tested commit, enable the image flag, repeat the three browser journeys against the deployed URL, then promote the exact same commit to production.

## Rollout And Rollback

The image enhancement flag remains off until local and deployed-preview browser checks pass. Production receives the schema before code and the flag after code health is confirmed. A rollback disables the flag first, preserving normalized uploads and all stored evidence, then restores the previous deployment if needed.

The existing production alias moves only after the three real-browser journeys pass on the deployed artifact. Multi-tenant concurrency work remains paused until this functional contract is accepted.

## Acceptance Criteria

- Photo input always displays normalized images and visibly uses an accepted enhanced cover when Gemini succeeds.
- URL input never directly publishes reference images and produces a reviewable generated cover when identity/reference data is sufficient.
- Description input either requests the exact missing identity facts or produces a reviewable generated cover.
- No successful analysis silently shows an unexplained empty gallery.
- Titles are factual, complete at the character boundary, non-repetitive, and use the strongest supported search terms.
- Descriptions retain useful commercial structure while containing only supported claims.
- Unpublished attributes can be reopened, edited, saved, and reflected in readiness.
- Real browser checks pass for all three inputs without publishing an ML item.
